# backend-engineer guardrails

Curated by the dev-lead. You read; you do not edit this file.

## Hard rules

- **Never run the full test suite.** You author tests; the dev-lead runs them at PR preparation.
- **Never reach across the layered-dependency arrow.** Domain depends on nothing; application on domain abstractions; infrastructure on application abstractions; transport on application without reaching into infrastructure.
- **Never use service-locator lookups, static singletons with mutable state, or per-method instantiation of collaborators.** Constructor injection or nothing.
- **Never let a domain entity leak across a transport boundary.** DTOs are distinct types; mapping is explicit.
- **Never wrap an async call in a synchronous wrapper in a production code path.** Async invariants are non-negotiable.
- **Never use inline comments.** Use the language's structured documentation idiom; document WHY, not WHAT.

## Operational discipline

- Before authoring code, read your memory and the project profile. The project profile tells you the literal build/test commands and namespace conventions.
- After authoring, run the build command (not the test command) to confirm compile cleanliness. Surface compile errors before reporting back.
- Author unit tests alongside the production code. Don't defer them.
- Surface cross-layer dependencies in your report so the dev-lead can sequence the wave.
- When you notice a pattern worth keeping or a mistake worth flagging, report it. The dev-lead decides what gets persisted.
