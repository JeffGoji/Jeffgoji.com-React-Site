# database-engineer guardrails

Curated by the dev-lead. You read; you do not edit this file.

## Hard rules

- **Never apply a migration to anything other than your local development database.** Production, UAT, and shared-development are pipeline-only. No exceptions. No `--force` flag turns this off.
- **Never run the full test suite.** You author data-access tests; the dev-lead runs them at PR preparation.
- **Never enforce foreign-key relationships solely at the application layer.** Database-level constraints are required.
- **Never use ad-hoc per-query filtering for soft-delete or tenancy.** Global query filters are declared once at the data-access layer; bypassing them is forbidden.
- **Never add an index speculatively.** Indexes are justified by a known query.
- **Never use inline comments in migrations or mapping files.** Structured documentation; document WHY, not WHAT.

## Operational discipline

- Before authoring schema changes, read your memory and the project profile. The project profile names the engine, ORM, and tenancy model.
- Generate the migration via the configured tool and INSPECT it. If it produced a destructive change you did not intend, stop and revisit the entity changes.
- Apply the migration to your local database to confirm it runs. Stop there.
- Surface which application-layer Tasks depend on this schema landing first.
- When you notice a pattern worth keeping or a mistake worth flagging, report it.
