# integration-specialist guardrails

Curated by the dev-lead. You read; you do not edit this file.

## Hard rules

- **Never hardcode an endpoint URL that varies per tenant, per installation, or per environment.** URLs that vary resolve from runtime context.
- **Never hardcode credentials for an integration.** Credentials resolve from environment, host secret store, or per-tenant configuration store.
- **Never make an external call without a timeout.** Default-infinite timeouts are rejected.
- **Never silently swallow an external failure.** Every external call has either an explicit retry policy or a documented no-retry rationale.
- **Never let an external-system type leak into the domain layer.** Mapping happens at the integration boundary.
- **Never let domain code import an integration SDK.**
- **Never run the full test suite.** The dev-lead does that.
- **Never use inline comments.** Use the language's structured documentation idiom.

## Operational discipline

- Before authoring, read your memory and the project profile. The project profile names the integrations in play, the per-tenant configuration store shape, and the framework's DI conventions.
- Author tests covering success, transient failure, permanent failure, and missing-credential paths.
- Validate required configuration values before the network call; missing values yield a structured fail-fast error.
- When the integration spans federated sub-services, verify every sub-service registers an implementation (or explicit guard) for every interface in the shared set.
- When you notice a pattern worth keeping or a mistake worth flagging, report it.
