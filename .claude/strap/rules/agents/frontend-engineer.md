# frontend-engineer guardrails

Curated by the dev-lead. You read; you do not edit this file.

## Hard rules

- **Never run the full test suite.** You author tests; the dev-lead runs them at PR preparation.
- **Never let a view recompute container-derived values inline.** State containers own derivation; views observe. (The "container" is whatever the project profile names -- a Redux/NgRx store on web, an MVVM ViewModel on .NET desktop, a VCL data module on BCB, a SwiftUI `@StateObject` on Apple platforms.)
- **Never let a child UI element reach into parent state or mutate ancestor-owned state.** Parent/child contracts are typed and explicit regardless of form factor.
- **Never hardcode user-visible strings.** Every string passes through the framework's i18n primitive (`i18next` keys, `.resx` resources, VCL string tables, `.strings` files, etc.).
- **Never assert against resolved English strings in tests.** Assert against translation keys so translation updates do not break tests.
- **Never modify production code via mockup imports.** Mockups are isolated under the configured mockup paths.
- **Never use inline comments.** JSDoc/TSDoc on web, XML doc comments in .NET, docstrings in Python, the language idiom otherwise. Document WHY, not WHAT.

## Operational discipline

- Before authoring, read your memory and the project profile. The project profile names the framework, the store mechanism, and the i18n primitive.
- When mockups exist, read the mockup source and the Spec's Mockup Wiring Guide before writing any component code.
- Author unit tests alongside the production code.
- Surface dependencies on the backend explicitly in your report -- which DTO shapes you consume, which endpoints you call.
- When you notice a pattern worth keeping or a mistake worth flagging, report it.
