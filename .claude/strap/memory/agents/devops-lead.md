## Project tradecraft

- **Deploy topology: single-target static deploy on Netlify.** No CI service, no container, no IaC -- correct for a personal SPA. Pipeline is: `git push` -> Netlify build image (`npm install` pulls `sharp` native binary + `fast-glob`) -> `npm run build` (`gallery:build` sharp resize -> `public/gallery/`, then `vite build` -> `dist/`) -> publish `dist/`.
- **Netlify's own build IS the CI/CD.** Do NOT add GitHub Actions -- it would duplicate the per-push build and create a second config to drift. Git repo since 2026-08-01 (`/connect-code-repo`); origin `https://github.com/JeffGoji/Jeffgoji.com-React-Site.git`.
- **`sharp` is the single most fragile build link** -- a native binary, Node-version-sensitive. Pinned to Node 22 as of Task 00046 (2026-08-01) -- check the LTS/EOL calendar before accepting a spec'd version number verbatim; Node 20 was already EOL (2026-04-30) when a Task literally specified it, and pinning it would have made local/Netlify *disagree* since the dev host runs 22. `sharp@0.34` engine range: `^18.17.0 || ^20.3.0 || >=21.0.0`. Only the `nd-totd2025` and `nd-hillcountry` galleries build through it.
- **Config files**: `netlify.toml` (command `npm run build`, publish `dist`), `public/_redirects` (`/* /index.html 200` SPA fallback -- correct), `public/_headers` (cache policy only).

## Anti-patterns to avoid

- **Unpinned Node version -- FIXED 2026-08-01 (Task 00046).** `.nvmrc` + `netlify.toml [build.environment] NODE_VERSION` now pin `22`.
- **`immutable` cache header on non-hashed originals -- PARTIALLY FIXED 2026-08-01 (Task 00046).** `public/_headers` rewritten from one broad `/gallery/*` rule (mid-path splat -- not Netlify's documented syntax; may never have matched, meaning `manifest.json` was inheriting `immutable` in prod) to four mutually exclusive `:placeholder`-syntax rules: `thumbs/*` and `display/*` stay `immutable` (unchanged from before), `original/*` gets `max-age=3600, must-revalidate`, `manifest.json` gets `max-age=300`. **Correction to this file's prior claim:** `thumbs/`+`display/` webp derivatives are NOT actually content-hashed either -- `build-gallery.mjs:57-58` emits `${filename}.webp` (raw source basename), same staleness mechanism as `original/`. They were left `immutable` because the Task's DoD required it, not because they're safe. **Open follow-up (unscheduled):** content-hash the derivative filenames in `build-gallery.mjs` so `immutable` on `thumbs/`/`display/` is genuinely correct -- natural home is Feature C Story 00044 (image-pipeline overhaul) when it's allocated.
- **Netlify `_headers` path syntax: use `:placeholder` for interior segments, never a mid-path `*`.** Splats (`*`) are trailing-only in Netlify's redirect/header rule syntax; a rule like `/gallery/*/manifest.json` is not guaranteed to match and rule-precedence between overlapping patterns is not something to rely on. Prefer mutually-exclusive explicit rules over one broad pattern + precedence.
- **Vestigial `target:'es2015'` -- FIXED 2026-08-01 (Task 00047), with a real regression caught and closed in the same Task.** The `Object.hasOwn` polyfill it sat next to in `main.jsx` was labelled SSR/jsdom residue but was actually load-bearing: `react-markdown` v10 calls `Object.hasOwn` at render time on every blog page. **`esbuild`'s `build.target` downlevels syntax only -- it never polyfills built-ins.** Deleting the polyfill and falling back to Vite's default target (safari14/chrome87/etc.) would have advertised a browser floor the bundle couldn't meet -- a hard `TypeError` on real (if uncommon) browsers, invisible to any check on a modern browser. Fixed by pinning an explicit, honest `build.target: ['chrome93','safari15.4','firefox92','edge93']` -- the actual floor `Object.hasOwn` needs -- documented via a `@remarks` JSDoc block above `defineConfig`. Also came out marginally smaller than the unpinned default. **Lesson: when deleting a config directive, verify its STATED rationale before trusting it** -- grep the built bundle for what the removal would actually expose; a comment can drift into covering a real requirement it never mentions. `entry-ssr.jsx` itself is still present (left alone deliberately, out of this Task's scope) -- deleting it is an open follow-up, and closing it should also prune the now-stale project-profile.md warnings about it and the es2015 coexistence caveat.
- **Headless render verification recipe for this host (no Chrome installed).** A `puppeteer-core` + `chrome-launcher` install works via `vite preview` + Edge: pass `executablePath: 'C:\\Program Files (x86)\\Microsoft\\Edge\\Application\\msedge.exe'`. Keep the install in a short path (`%TEMP%\lh` or similar) -- same Windows MAX_PATH reasoning as the Lighthouse note below. To prove a global script (e.g. AdSense) actually EXECUTED rather than merely sitting inert in the DOM, check `typeof window.<global> === 'object'`/`'function'` at runtime, not just tag presence in the markup.
- **Half-consumed gallery pre-build.** `build-gallery.mjs:33-44` builds two galleries; `nd-hillcountry`'s sharp output is regenerated every build but NEVER referenced (the HillCountry component uses `import.meta.globEager` static imports + runtime canvas thumbnailing instead). Wasted build time + CDN storage, and two parallel thumbnail systems. Pick one.
- **Hardcoded `GALLERIES` list** (`build-gallery.mjs:33`) with `srcDir` paths that must exist. Rename a dir -> `fast-glob` returns empty -> silently ships an empty manifest (`count:0`, no error). Add a "0 items found" guard. (Per-file error handling IS good -- bad images skipped and recorded in `manifest.skipped`.)
- **Missing security headers** on `public/_headers` -- policy owned by security-reviewer; the header block is the deploy surface. Add `nosniff`, `Referrer-Policy`, HSTS, `frame-ancestors`, and an AdSense-permissive CSP.

## Tool / environment quirks

- Windows dev host; on Windows prefer the PowerShell tool for native ops and Bash for portable text ops.
- Gallery build output (`public/gallery/`) is gitignored and regenerated from scratch every build (~186 images; seconds, scales linearly). No idempotency/caching -- fine at current scale.
- **`npm install --prefix <worktree-path>` (run from outside the worktree) silently injects a self-referential file: dependency into `package.json`** (e.g. `"jeffgoji-com": "file:../../../<repo-name>"`) plus stray `package-lock.json` churn, and leaves a `node_modules/<pkg-name>` symlink/junction pointing back at the parent repo that a `package.json` revert does NOT clean up (check for it explicitly, don't just trust a clean `git diff`). **npm is the one exception to the general "prefer absolute paths over compound `cd &&`" shell habit** -- npm's only path-targeting flag IS `--prefix`, which is exactly what causes this corruption, so for npm specifically: `cd` into the worktree first (subshell or otherwise) and never pass `--prefix`. Check `git status` before staging to confirm `package.json`/`package-lock.json` are untouched unless you meant to change deps.
- Deeply nested `git worktree add` paths under this repo's long directory name can exceed Windows' 260-char path limit (this repo has some long legacy image filenames). `git config core.longpaths true` on the repo fixes it.
- Ensure `.nvmrc`/text config files land LF-normalized even with Windows `autocrlf` on -- a CRLF `.nvmrc` blob ships `20\r` (or similar) to Netlify's Linux build image and can break version resolution. Verify before pushing.
- **Lighthouse on this host needs two specific workarounds (Task 00048).** (a) The Lighthouse *CLI* does not run on Node 22.14 -- `ERR_REQUIRE_CYCLE_MODULE` in `puppeteer-core`. Use the Lighthouse Node API directly instead; it never loads the broken path. (b) **Windows MAX_PATH breaks Lighthouse silently.** Node reads a nested `core/lib/cdt/package.json` CommonJS type-marker at ~66 chars of path suffix; past 260 total chars that read fails with no filesystem error, and every audit then dies with a misleading `SDK.js does not provide an export named 'default'`. The per-session scratchpad path is too long for this -- use a short path like `%TEMP%\lh` instead. Generalizes: any npm tool with nested `package.json` type markers will break the same way if installed into the scratchpad path on this host.
- Real Lighthouse audits against `vite preview` (localhost) give production-accurate byte/format figures (image weight, format savings) but NOT production-accurate connection-driven figures (TTFB, LCP timing) -- no CDN, no real handshake, `_headers`/`_redirects` unapplied. For AC-007/AC-008-grade LCP numbers, run against the live deployed URL.
